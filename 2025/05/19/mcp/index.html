什么是MCP

引言

如今的大型语言模型 （LLM） 在现实当中非常智能，但一旦它们需要超出冻结训练数据中的信息，它们就会陷入困境。要使 AI 代理真正有用，它们必须在正确的时间访问正确的上下文（无论是您的文件、知识库还是工具），甚至根据该上下文执行更新文档或发送电子邮件等作。从历史上看，将 AI 模型连接到所有这些外部来源一直是一件混乱的临时工作。开发人员必须为每个数据源或 API 编写自定义代码或使用专用插件。这使得 “wire together” 集成变得脆弱且难以扩展。

为了简化这一过程，Anthropic 推出了模型上下文协议（MCP）——一个开放标准，旨在将 AI 助手与数据和工具世界连接起来，让其能够接入多种不同的上下文来源。他们在 2024 年 11 月宣布了这一协议，起初市场反应平平。但现在 MCP 正在迅速流行，已经超过 Langchain，并且有望在不久的将来超越 OpenAPI 和 CrewAI。主要 AI 参与者和开源社区纷纷支持 MCP，认为它可能会成为构建具备自主能力的 AI 系统的革命性技术。为什么会这样呢？

在这篇文章中，我们将深入探讨 MCP（模型上下文协议）——为什么它目前成为热门话题，MCP 如何推动 AI 向更加集成、具备上下文感知的方向发展，以及它在自主代理工作流中的作用。此外，我们还会揭示一些鲜为人知的细节，这些是开发者、研究人员、AI 工程师和科技高管应该关注的内容。同时，我们还将探索一些创新性的 MCP 应用，其中许多尚未被广泛尝试。

为什么 MCP 现在掀起浪潮（而不是去年 11 月）？

MCP 由 Anthropic 在 2024 年 11 月底首次开源并发布。当时，它是一个令人兴奋的概念，但并没有引起太多关注或被认真对待。直到 2025 年初，MCP 才真正进入 AI 社群的视野，引发广泛讨论。这一波热潮的主要原因包括：

解决集成问题：AI 代理和自主工作流在 2023-2024 年间成为热门话题，但它们的最大短板一直是：如何与现实世界的业务系统和数据进行集成。最初，人们的关注点主要集中在模型能力和提示技术上，而不是数据和系统集成。MCP 则精准填补了这一空白，它定义了“如何将现有数据源”（文件系统、数据库、API 等）接入 AI 工作流。随着人们深入研究 MCP，它逐渐被视为让 AI 代理真正进入生产环境的关键拼图。（这是 HumanX 会议上的一个观点：近年来，我们主要关注构建独立的 AI 模型，每个模型都专注于特定任务。但随着复杂性和需求的增长，AI 开发正在向集成系统转变，即由多个专门模型、软件组件、API、数据源和界面协调合作的体系。）

社区发展与应用普及：在短短几个月内，MCP 从概念变成了一个不断增长的生态系统。早期采用者包括 Block（Square）、Apollo、Zed、Replit、Codeium 和 Sourcegraph 等公司，它们开始集成 MCP 以增强自身平台。到了 2025 年，生态系统呈现爆发式增长——到 2 月，已有超过 1,000 个社区构建的 MCP 服务器（连接器）可用。很明显，MCP 的崛起符合行业向更集成化、具备上下文感知的 AI 方向发展的趋势。这种网络效应使得 MCP 更具吸引力：可用的工具越多，采用 MCP 标准的价值就越大。

迈向事实上的行业标准：与其他专有 SDK 或零散框架不同，MCP 是开放的、模型无关的，并且由知名 AI 公司支持。这意味着任何 AI 模型（Claude、GPT-4、开源 LLM 等）都可以使用 MCP，任何开发者或公司都可以创建 MCP 集成，而无需获得许可。许多社区成员认为 MCP 很可能会成为AI 系统连接外部数据的标准——类似于 USB、HTTP 或 ODBC 成为各自领域的通用标准。

快速发展与教育推广：Anthropic 并没有发布 MCP 后就不管不问，他们一直在积极改进 MCP 并教育开发者。在最近的 AI 峰会上，Anthropic 的 Mahesh Murthy 举办了一场爆火的 MCP 研讨会，进一步推动了 MCP 的采用。（文末还包含所有相关学习资源链接，供读者深入了解。）

MCP 的崛起不仅是技术上的突破，也是社区推动、行业需求和开放标准趋势共同作用的结果。你怎么看 MCP 未来的发展？

MCP（模型上下文协议）是什么，它是如何工作的？

MCP 设定了明确的规则，规定 AI 如何查找、连接并使用外部工具——无论是查询数据库还是执行命令。借助 MCP，AI 不再仅仅局限于其训练数据，而是能够突破固有信息的限制，让模型更加灵活，并能够感知和利用周围的真实世界信息。

MCP 的技术概述：

MCP 具有一个显著特性——动态发现，即 AI 代理可以自动检测可用的 MCP 服务器及其能力，而无需进行硬编码集成。例如，如果你启动一个新的 MCP 服务器（比如 CRM），AI 代理可以立即识别并使用它，通过标准化 API 进行连接。这种灵活性远超越传统集成方式，使得 AI 代理能够适应不断变化的系统和数据源。

如何开始使用 MCP？

最好的起点是官方 MCP 文档和代码库。Anthropic 已开源了 MCP 规范，并提供了 SDK（支持 Python，现在甚至包括 Java）。一般来说，入门步骤如下：

  1. 运行或安装 MCP 服务器，用于管理你需要的工具或数据源。Anthropic 在开源代码库中提供了预构建的 MCP 服务器，涵盖 Google Drive、Slack、Git、数据库等流行系统。你可以安装这些服务器，并进行配置（通常只需运行命令并提供凭据或密钥）。

  2. 在你的 AI 应用中设置 MCP 客户端。如果你在使用 Claude 的应用，可以直接在 UI 中添加 MCP 服务器。如果你在编写自己的 AI 代理，可以通过 MCP SDK 连接到服务器（提供地址和端口）。

  3. 启用 MCP 服务后，AI 代理会自动发现并利用 MCP 服务器提供的附加功能，如新工具、资源和提示模板，使 AI 具备更强的上下文处理能力。

  4. 调用并迭代优化。你的 AI 模型或代理可以随时调用 MCP 提供的工具。你可以监控日志，确保正确调用 MCP 服务器，并查看请求和响应数据，以优化集成效果。

如果你想快速入门，Anthropic 建议尝试Claude Desktop 集成（如果你有访问权限），或者运行示例服务器，并使用其快速入门指南。此外，MCP 社区非常活跃，已构建了大量 MCP 服务器，涵盖 Google 服务（Drive、Gmail、Calendar）、Slack（聊天与文件访问）、GitHub/Git（代码库管理）、Postgres 数据库、Web 浏览器（如 Puppeteer），以及更多工具。许多 MCP 服务器都被列在社区目录中（一些开发者创建了专门的索引网站）。你也可以在官方 MCP GitHub 上找到许多连接器实现，帮助你快速上手。

如果 MCP 还没有适配你所需的工具，你可以使用 SDK 构建自己的 MCP 服务器——通常，它只是一个对该工具 API 的轻量封装，并以 MCP 兼容的格式公开相关功能。

在 MCP 之前，AI 系统是如何处理上下文和工具访问的？

让我们简要回顾一下传统方法如何为 AI 提供外部知识或执行操作，以及 MCP 如何与之不同：

  • 自定义 API 集成（一次性连接器）：最常见的方法是为每个服务编写自定义代码或使用 SDK。例如，如果你希望 AI 代理访问 Google Drive 和 SQL 数据库，你必须分别集成 Google API 和数据库驱动程序，每个都有自己的身份验证、数据格式和操作方式——非常麻烦！而 MCP 提供了一个通用协议，类似于一把万能钥匙，可以解锁多个系统，并且无需修改客户端即可添加新的 MCP 服务器。

  • 语言模型插件（OpenAI 插件等）：2023 年引入的一种方法是让模型使用标准化的插件规范（通常是 OpenAPI 方案），从而受控地调用外部 API（例如 ChatGPT 插件系统）。尽管与 MCP 有类似的目标（标准化工具访问），但这些插件通常是专有的，且局限性较大——每个插件仍然需要单独构建和托管，并且只有某些特定平台（如 ChatGPT 或 Bing Chat）可以使用。此外，插件通常只支持单向数据检索（模型调用 API 获取信息），而无法保持持续的互动。MCP 的优势在于开源和通用性（任何人都可以实施，不依赖于某个 AI 提供商），并且支持双向交互，它像是 AI 和工具之间的对话，而插件更像是无状态的问答调用。

  • 工具使用（LangChain 工具、AI 代理）：LangChain 等代理编排库推动了 AI 工具调用的概念，即模型可以使用定义好的工具（函数），比如 search() 或 calculate()，代理（LLM）决定何时调用。这很强大，但每个工具仍然需要自定义实现——LangChain 的库已经扩展到 500 多种工具，虽然接口统一，但开发者仍然需要手动连接这些工具，确保它们适用于自己的需求。MCP 在这里是互补的：它提供了工具的标准化接口，而 MCP 服务器可以看作是现成的工具库，任何 AI 代理都可以使用。区别在于标准化的方式：LangChain 为开发者提供了标准（Tool 类接口），用于在代理代码中集成工具；MCP 为模型提供了标准——运行中的 AI 代理可以在执行时发现并使用任何 MCP 定义的工具，即使代码没有针对某个工具进行自定义集成，模型也可以动态使用它。实际上，这些方法正在趋同：LangChain 团队在 MCP 崛起后开发了适配器，让所有 MCP 服务器（连接器）都可以被当作 LangChain 工具使用。因此，使用 LangChain 或其他框架构建的代理可以直接调用 MCP 工具，并受益于日益增长的 MCP 生态系统。

  • 检索增强生成（RAG）和向量数据库：一种常见的向 AI 供应上下文的方法是使用检索器（retriever），搜索知识库（文档、嵌入）并将最相关的结果注入到模型的提示词中，以弥补 AI 的知识截止点或有限记忆。然而，RAG 主要处理静态文本片段，它不会让模型执行超出索引范围的操作或查询。MCP 实际上可以与 RAG 协同工作——例如，一个 MCP 服务器可以连接向量数据库或搜索引擎，使模型能够像调用工具一样执行搜索查询，而不仅仅是每次都依赖检索被动获取上下文。可以说，MCP 是一种更通用的机制：RAG 主要提供被动上下文，而 MCP 使模型能够主动获取或执行操作。在需要最新或交互式数据的场景（比如查询实时数据库或发布更新）时，MCP 超越了单纯的检索文本——它能够触发实际操作。

MCP 的出现，让 AI 能够更主动地与外部系统交互，而不仅仅是被动获取信息。你觉得 MCP 能在哪些场景中带来最重要的突破？

MCP 是万能方案吗，能解决所有问题吗？

当然，MCP 不是万能钥匙，而是一个极为便利的集成层。但和所有新兴技术一样，它也引入了一系列复杂性和挑战，开发者和组织在大规模采用前必须仔细考虑：

  • 工具服务器管理的额外开销：运行和维护多个 MCP 服务器可能非常繁琐，尤其是在生产环境中，稳定性、安全性和可扩展性至关重要。MCP 的最初实现主要面向本地和桌面使用，因此如何适配云架构和多用户场景仍然是个开放问题。开发者已经提出让 MCP 更无状态并适配分布式环境的方案，但这仍然是持续挑战。

  • 工具可用性问题：MCP 扩展了 AI 模型的工具集，但并不意味着模型能够有效利用这些工具。此前的代理框架表明，AI 模型可能在工具选择和执行方面存在困难。MCP 试图通过结构化工具描述和规范来缓解这一问题，但成功仍然取决于描述的质量及 AI 正确解析这些信息的能力。LangChain 创始人 Harrison Chase 提出的社区驱动方式认为，完善的工具文档可以提升可用性，但这仍然需要持续优化。

  • MCP 的技术成熟度：作为新兴技术，MCP 仍在快速演进，这可能会带来破坏性更新，导致服务器和客户端需要频繁升级。尽管 MCP 的核心概念相对稳定，但开发者应该预期并适应版本更新以及不断变化的最佳实践。

  • 兼容性问题：目前，MCP 在 Anthropic 生态系统（Claude等）中获得了一流支持，但更广泛的应用仍不确定。其他 AI 供应商可能不会原生支持 MCP，这需要额外的适配器或自定义集成。在 MCP 被更广泛采用之前，它的实用性仍然会受到一定限制。

  • 适用场景限制：对于较简单的应用，MCP 甚至可能过于复杂。如果 AI 只需要访问一两个简单 API，直接调用 API 可能比 MCP 集成更高效。此外，MCP 的消息系统和服务器配置有一定学习曲线，开发者需要权衡 MCP 的优势和复杂性。

  • 安全性和监控问题：由于 MCP 充当中间层，它需要强大的身份验证和权限控制来防止未经授权访问。类似 MCP Guardian 的开源项目已开始解决这些问题（比如请求日志记录和策略执行），但确保 MCP 在企业环境中的安全性仍是待完善的领域。

总体而言，这些问题并不会阻碍 MCP 的发展，但建议从实验性或非关键性部署开始，以积累经验。MCP 最大的优势之一是活跃的社区，由于它是开源的，你遇到的任何问题都可以通过社区协作解决。

MCP 在自主编排中的作用及其在自主工作流中的位置

在之前的文章中，我们探讨了自主代理（Agent）的核心构建模块：画像（身份与上下文）、知识、记忆、推理/规划、反思以及行动。一个智能代理需要：

  • 观察和理解环境（画像/知识）
  • 记住过去的交互（记忆）
  • 规划自己的行为（推理/决策）
  • 执行动作（调用工具或输出）
  • 反思并学习（调整策略）

那么，MCP 在哪里发挥作用？

MCP 本身不是一个“代理框架”，而是一个标准化的集成层，专门用于处理行动（Action）部分——让代理以标准化的方式执行涉及外部数据或工具的操作。它提供了安全、结构化的连接方式，使 AI 代理能够顺畅地接入外部系统和工具。如果没有 MCP（或类似技术），每次代理需要在现实世界执行任务——比如获取文件、查询数据库或调用 API——开发者都必须编写自定义集成代码或使用临时解决方案，这就像为一个机器人单独定制每一根手指，以便抓取不同的物体，不仅繁琐，而且无法扩展。

需要再次强调，MCP 不是编排引擎，也不是 AI 代理的“大脑”，而是代理架构中的集成层。它补充了 LangChain、LangGraph、CrewAI 和 LlamaIndex 等代理编排工具，充当 AI 代理的统一“工具箱”，让代理能够调用外部操作。MCP 不会取代编排引擎（后者决定代理何时以及为什么使用工具），而是定义工具如何被调用及数据如何交换。

MCP 类似于一个标准化的 API 网关，将集成复杂度从“N×M”问题（每个代理对接多个工具）降低为“N+M”问题（所有代理使用统一协议调用所有工具），从而实现客户端（AI 代理）和服务器（工具）的通用兼容性。最终，MCP 简化了外部功能的集成，让 AI 代理更加多功能、可适应，并能够在不同的环境中执行复杂任务。

MCP 解锁的新可能性

MCP 仍然处于早期阶段，其全部潜力才刚刚开始被探索。首批应用场景显而易见——例如将企业数据连接到聊天助手，或增强编码代理的代码库访问能力。但一些新兴应用可能会将 AI 代理提升至新的高度：

  • 多步骤、跨系统工作流
    代理系统通常需要跨多个平台进行协调。例如，当 AI 计划一个活动时，它需要检查日程表、预订场地、发送邀请邮件、安排交通，并更新预算表。目前，这些操作必须手动拼接多个 API。而 MCP 让所有这些任务通过单一接口完成——代理可以依次调用 MCP 工具（每项任务对应一个工具），确保共享上下文，无需定制化集成，也不会出现断点丢失数据的问题。

  • 理解环境的智能代理（包括机器人）
    除了访问工具，MCP 还能让 AI 代理嵌入智能环境（如智能家居或操作系统）。AI 助理可以通过标准化的 MCP 服务器与传感器、物联网设备或操作系统功能交互，使 AI 具备实时环境感知能力，从而提供更自然且主动的帮助。

  • 协作式代理（智能代理网络）
    MCP 还能充当多代理系统的共享工作空间。专门化的 AI 代理（如负责研究、规划、执行的不同代理）可以通过 MCP 交换信息并动态协调任务。借助 MCP，每个代理无需直接集成各自的工具，而是可以访问统一的工具集。

  • 深度集成的个人 AI 助理
    MCP 可以让用户安全地配置自己的 AI 助理，使其与个人数据和应用交互。例如，本地 MCP 服务器可以赋予 AI 对电子邮件、笔记和智能设备的访问权限，而不会将敏感数据暴露给第三方。这可能创造出高度个性化的 AI 助理，且无需依赖云服务。

  • 企业级治理与安全
    对企业而言，MCP 标准化了 AI 访问内部工具的方式，降低了集成开销。此外，它还能实现治理——AI 交互可被记录、监控和控制，通过监督层防止意外操作，同时保持高效工作流。

这些只是 MCP 潜力的初步体现。它通过流畅、具备上下文意识的多步骤交互，让 AI 代理更接近真正的自主工作流执行。

总结思考

MCP 正在迅速发展成为一个强大的标准协议，让 AI 不再是孤立的“思维体”，而是一个多功能的“执行者”。它通过简化代理连接外部系统的方式，为更强大、互动性更强、用户友好的 AI 工作流铺平了道路。

MCP 的崛起甚至让我们调整了编辑计划，因为它的影响力实在太值得深入探讨！在探讨了 代理工作流中的“行动” 之后，解析 MCP 似乎是再自然不过的事情。下一篇，我们将深入研究人机交流和“人类参与”（HITL）集成，然后进入多代理协作的主题。
