

## 引言
选择正确的开源 LLM 并不是要找到“最佳”模型，而是要找到真正适合您的特定用例、硬件、预算和约束的模型。本指南将引导您了解重要的真正决策标准，从性能基准到实际部署注意事项。为了超越理论，该指南展示了如何使用 AI Sheets 来试验数千个模型和最佳推理提供商。

## 本指南为何存在

Hugging Face 上有超过 200 万个公共模型，并且每周都会发布新版本，选择开源 LLM 可能会让人感到不知所措。大多数指南只列出了流行的模型，但这并不是真正的选择方式。您需要一个考虑实际约束和要求的框架。

人们犯的最大错误是什么？根据排行榜和基准选择模型，而不是使用实际数据进行测试。在 MMLU 上得分为 82% 的模型可能会在您的特定领域、写作风格或边缘情况下完全失败。

## 你需要先弄清楚什么

在深入研究模型比较之前，请回答以下问题：

**硬件约束**

* 你的 GPU 情况如何？（这比你想象的更重要）
* 您是在本地运行还是在云中运行？
* 您实际拥有多少 VRAM？

**用例细节**

* 你的首要任务是什么？（编码、写作、分析、聊天）
* 响应速度与质量有多重要？
* 您需要多模态功能吗？

**实际限制**

* 您的推理成本预算是多少？
* 您需要微调功能吗？
* 有任何合规性或数据隐私要求？

## 真正的选择标准
**1. 任务性能（但不仅仅是基准测试）**

不要只看 MMLU 分数。不同的模型擅长不同的任务：

对于编码：查看 HumanEval 和 SWE-bench 分数，但也要在实际代码库上进行测试

写作：查看 EQBench Creative Writing 和 WritingBench 进行风格和创造力评估，但也可以根据您的具体写作要求进行测试

对于助手和文本处理：测试特定于领域的问题的推理能力

专业提示：使用实际用例中的示例创建一个小型评估集。它比任何公共基准测试都更有价值。

**2. 硬件要求**
这是大多数人搞砸的地方。了解 VRAM 要求有助于您是在本地运行还是选择云实例。

模型大小与功能权衡：

|型号尺寸	|显存 （FP16）|	VRAM（4 位）|	云选项|	本地硬件|	最佳用例|
|-----------|----------|----------|----------|----------|----------|
|1–3B|	4–6 GB|	~2 GB|	AWS g4dn.xlarge，基本 GPU 实例|	RTX 3060，笔记本电脑 GPU|	基本聊天、文本分类、自动完成|
|7-8B|	14–16 GB|	~6–8 GB|	AWS g5.xlarge，RunPod RTX 4090|	RTX 4080/4090、A6000|	通用助手、摘要、编码|
|13-14B|	26–28 GB|	~12–16 GB|	AWS g5.2xlarge，多实例|	RTX 4090（仅量化）|	更强的推理，更好的指令遵循|
|70B+|	140 GB+|	~35–40 GB|	AWS p4d.24xlarge、A100 集群	|多 GPU 设置（昂贵）	|SOTA 推理、企业应用|

## 量化注意事项：

* 4 位量化将内存减少到原始内存的 ~25% - 7B 型号从 ~14GB 下降到 ~3.5GB
* 8 位量化将内存需求减半，质量损失最小
* 量化会降低一些质量，但对于大多数应用来说通常是可以接受的

## 3. 推理速度和提供商性能
除了硬件要求之外，推理速度在提供商之间差异很大，并影响用户体验。

**提供商比较：**

|提供程序类型	|特性	|最适合|
|-------------|-----|------|
|优化的提供商（Groq、Cerebras）|	超快的专用硬件	|实时应用程序、交互式聊天、速度关键型工作流程|
|标准云（AWS、Azure、GCP）	|以企业为中心	|规模化生产、合规要求、企业集成|
|一般推理（Together AI、Replicate）|	均衡的产品|	开发和测试、多样化的模型访问、经济高效的扩展|
|本地部署|	您的硬件	|隐私敏感数据，无限使用，完全控制|

**重要的速度因素：**

* 型号尺寸：较大的型号速度较慢 - 70B 型号通常比 7B 慢 3-5 倍
* 上下文长度：较长的提示会显着减慢首次令牌时间
* 批处理：多个用户的吞吐量与延迟权衡
* 地理位置：延迟因提供商区域而异

**真实世界的速度示例：**

* 聊天应用程序：需要快速响应时间才能获得良好的用户体验（感觉响应迅速）
* 代码生成：中等速度是可以接受的，因为用户会阅读
* 批处理：吞吐量比单个响应速度更重要
* 流媒体：快速的首次token时间对于实时感觉至关重要

## 4. 部署复杂性
**本地部署**

* 更易于启动，完全控制数据
* 受硬件限制
* 考虑 vLLM 或 llamacpp 等工具，以便于设置
  
**推理提供商（中间商）**

* 使用 Hugging Face 推理提供商通过优化的提供商（如 Groq、Cerebras、Together AI）访问模型
* 按使用付费定价，无需基础设施管理
* 非常适合测试和适度生产使用
* 易于在提供商和型号之间切换

**云部署**

* 更具可扩展性，可以处理更大的模型
* 持续成本，但比硬件投资更可预测
* 满足企业需求的 Hugging Face 推理端点等服务。
  
**成本考虑：**

* 推理提供商：每 0.001K 代币 0.001-0.01 美元，具体取决于模型大小
* 本地硬件：前期成本高，但使用无限制
* 大多数团队从推理提供商开始，仅针对特定的隐私需求迁移到本地

## 5. 社区和生态系统

**积极发展**

* 定期更新和错误修复
* 社区对问题的支持
* 可用的微调资源和指南

**集成选项**

* API 兼容性（OpenAI 格式常见）
* 框架支持（转换器、vLLM 等）
* 工具生态系统（代理、RAG 框架）

**要避免的常见选择错误**

* 错误 1：追逐最新型号最新版本并不总是最稳定或支持良好的版本。有时，以前的版本对于生产使用来说更可靠。

* 错误 2：忽略推理速度需要 30 秒才能响应的模型在技术上可能更好，但对于交互式应用程序来说实际上毫无用处。

* 错误 3：没有使用真实数据进行测试综合基准测试无法捕获您的特定领域、写作风格或边缘情况。使用您的实际数据来测试模型 - 像 AI Sheets 这样的工具比设置复杂的测试管道要容易得多。

* 错误 4：低估了部署复杂性在笔记本中运行模型与大规模可靠地提供模型不同。考虑通过 Hugging Face 推理提供程序从托管推理开始，在构建自己的基础设施之前在类似生产的条件下进行测试。

## 实用的选择过程

**第 1 步：定义约束**

写下您的硬件限制、延迟要求和预算。这些是硬性约束，可以立即消除许多选项。

**第 2 步：根据任务绩效列出候选名单**
查看在您的特定任务类型上表现良好的模型。从最多 3-5 个候选人开始。

**第 3 步：使用真实数据进行测试（这就是 AI Sheets 的用武之地）**
使用实际用例中的示例创建一个小型评估集。您可以使用 AI Sheets 并排比较模型，而不是设置复杂的测试基础设施。

**如何使用 AI Sheets 进行模型比较：**

* 导入您的测试数据 - 上传包含评估提示/问题的 CSV
* 创建比较列 - 为要测试的每个模型添加一列，提示如下：“回答以下内容：{{prompt}}”测试问题在哪里prompt
* 选择您的推理提供程序 - AI Sheets 通过 Hugging Face 推理提供程序连接到多个提供程序（Groq、Cerebras、Together AI 等），因此无需任何本地设置即可测试模型
* 并排比较结果 - 了解不同模型如何处理电子表格格式中的相同输入
* 添加 LLM 评委 - 创建另一列，其中包含以下提示：“评估这些响应：{{prompt}}。响应 1：{{model1}}。响应 2：{{model2}}。哪个更好，为什么？
* 迭代和优化 - 编辑单元格以提供良好输出的示例，然后重新生成以查看模型是否改进
* 这优于设置单独的 API 调用和手动比较输出。您可以获得清晰的视觉比较，并可以轻松地跨多个模型测试数十个示例。

专业提示：Hugging Face 推理提供程序可让您通过优化的提供程序访问数千个开源模型 - 在评估期间无需下载或托管任何内容。

**第 4 步：考虑总拥有成本**

考虑推理成本、潜在的微调需求和维护开销。

**第 5 步：从小处着手，逐步扩大规模**

从满足您要求的最简单解决方案开始。您可以随时稍后升级。

## AI Sheets 推荐型号
AI Sheets 有一个推荐模型部分，重点介绍了当前不同类别的高性能开源模型：

**通用和推理：**

* openai/gpt-oss-20b - 轻量级通用模型
* openai/gpt-oss-120b - 更强的推理能力
* meta-llama/Llama-3.1-70B-Instruct - 全面的旗舰模型
  
**编码专家：**

* Qwen/Qwen3-Coder-480B-A35B-Instruct - 最先进的编码性能
  
**专业任务：**

* CohereLabs/command-a-translate-08-2025 - 翻译任务
  
请记住：这些是测试评估过程的示例，而不是永久建议。使用 AI Sheets 比较这些模型在您的特定用例和数据上的性能。

## 未来呢？
开源 LLM 格局瞬息万变。选择“完美”模型更重要的是构建一个选择和评估过程，您可以在新模型出现时重复。

专注于创建良好的评估数据集和部署管道，而不是将所有赌注押在单个模型选择上。

## 后续步骤

* 使用上述框架定义您的需求
* 使用您的真实数据测试 2-3 个候选模型（尝试使用 AI Sheets，使用 Hugging Face 推理提供程序轻松并排比较）
* 从满足您需求的最简单的解决方案开始 - 通常在自托管之前进行托管推理
* 监控性能并准备好随着需求的变化进行切换
* 最适合您的项目的开源 LLM 是能够为您的用户实际发布并可靠地工作的 LLM。其他一切都是优化。
